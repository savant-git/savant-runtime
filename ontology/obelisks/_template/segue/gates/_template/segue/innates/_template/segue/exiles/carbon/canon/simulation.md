# carbon simulation

## status

active

## owner

carbon

## singular purpose

carbon owns advanced proprietary simulation.

carbon is the generalized savant evolution of the original oriel concept.

oriel established the originating simulation idea. carbon expands that idea into a reusable simulation substrate capable of representing and executing arbitrary composed systems rather than remaining confined to a single simulation application or domain.

## primitive

carbon's primitive is the simulation instance.

a simulation instance is an addressable execution context composed from referenced entities, state, parameters, constraints, relationships, events, temporal conditions, dependencies, and declared simulation rules.

simulation instances are substantiated once and may be reused, attached, branched, replayed, compared, or composed without duplicating their underlying authoritative sources.

## simulation domains

carbon is domain-independent.

a carbon simulation may represent:

- characters
- identities
- populations
- environments
- spaces
- physical systems
- social systems
- organizations
- economies
- narratives
- conversations
- relationships
- behaviors
- workflows
- software systems
- operational systems
- temporal processes
- hypothetical conditions
- counterfactual histories
- future scenarios
- synthetic worlds
- embodied entities
- combinations of other simulations

domain-specific behavior attaches to carbon rather than redefining carbon.

## execution

carbon may execute a simulation through discrete steps, events, continuous progression, bounded iterations, parameter sweeps, or attached execution engines.

execution must preserve the exact simulation identity and sufficient execution inputs for replay whenever deterministic replay is supported by the participating components.

## branching

any eligible simulation state may become a branch point.

a branch receives its own identity and retains:

- parent simulation
- parent branch
- branch point
- originating state
- changed parameters
- injected events
- constraints
- dependencies
- provenance
- lineage

branches never overwrite their ancestors.

## counterfactuals

counterfactuals are explicit simulation branches.

they remain distinguishable from observed history and accepted authority.

carbon may answer what could happen under declared assumptions.

carbon must not silently transform could into did.

## checkpoints

carbon may checkpoint simulation state.

a checkpoint is an immutable reference point suitable for replay, comparison, branching, recovery, or inspection.

## replay

replay reconstructs simulation execution from preserved primitives, parameters, state, dependencies, events, and execution semantics.

replay must expose divergence when deterministic reconstruction is impossible.

## comparison

carbon may compare:

- branch against branch
- checkpoint against checkpoint
- simulation against simulation
- simulated state against an admitted external observation
- parameter set against parameter set
- outcome against outcome

comparison is projection and does not alter either compared object.

## interrogation

a simulation may be queried for:

- current state
- prior state
- branch history
- causal path
- dependencies
- dependents
- parameters
- constraints
- injected events
- uncertainty
- divergence
- provenance
- lineage
- projected outcomes

## composition

simulations may contain or reference other simulations.

higher-order simulations emerge through composition rather than duplication.

an entity substantiated elsewhere should be referenced whenever reference preserves the required semantics.

## uncertainty

uncertainty must remain explicit.

carbon must preserve distinctions among:

- known input
- admitted evidence
- assumption
- parameter
- inferred value
- stochastic value
- simulated state
- projected outcome
- counterfactual
- unknown

## receipts

simulation execution may emit immutable receipts containing sufficient metadata to identify:

- simulation
- branch
- checkpoint
- execution
- inputs
- parameters
- dependencies
- engine
- start state
- resulting state
- lineage
- provenance
- deterministic status

a receipt proves that a simulation operation occurred.

it does not prove that the simulated result is true in external reality.

## avatar forge

avatar forge is a carbon-owned simulation application.

its embodiment functionality is one specialization of carbon's generalized simulation substrate.

avatar forge does not define carbon's overall purpose.

## authority invariant

simulation is not observation.

simulation is not accepted authority.

simulation output is derived structure.

carbon owns simulation mechanics and simulation state.

source authorities continue to own the primitives carbon references.

composition, execution, branching, replay, comparison, and projection do not transfer authority.
