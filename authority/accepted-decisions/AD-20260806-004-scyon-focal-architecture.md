# AD-20260806-004: Scyon and Focal Architecture

## Status

Accepted

## Date

2026-08-06

## Authority

Current user directive.

## Decision

Savant adopts **Scyon** as the canonical term for its modular three-dimensional database organism.

Savant adopts **Focal** as the canonical term for the specialized top layer applied to a Scyon.

The canonical relationship is:

`shared Scyon kernel + tier profile + metadata + ability modules + equalizer state + Focal = operational Scyon`

The terms supersede weaker implementation terminology as follows:

| Superseded term | Canonical term |
|---|---|
| dimensional database | Scyon |
| dimensional database kernel | Scyon kernel |
| dimensional database instance | Scyon instance |
| custom overlay | Focal |
| overlay instance | Focal instance |
| overlay identifier | Focal identifier |
| overlay kind | Focal kind |

Historical implementation names remain compatibility evidence until a separately validated migration replaces them.

## Core architectural law

Every Scyon is fundamentally an instance of one shared modular kernel.

Scyons must not be independently reconstructed as unrelated database implementations.

Differences among Scyons arise through composition of:

1. identity-tier capacity;
2. one Focal;
3. enabled ability modules;
4. metadata;
5. metadata interpretation rules;
6. equalizer configuration;
7. authority and policy constraints;
8. constituent and dependent relationships;
9. runtime resource limits;
10. projection requirements.

The shared kernel remains canonical substance.

A Focal extends the shared kernel without copying, replacing, weakening, or independently reimplementing it.

## Three-dimensional model

A Scyon stores and operates across three inseparable dimensions.

### Identity dimension

The identity dimension establishes what an element is.

It includes:

- stable identity;
- identity tier;
- archetype;
- constituent identities;
- owning identity;
- lineage;
- succession;
- compatibility.

### State dimension

The state dimension establishes what an element currently contains, asserts, permits, or performs.

It includes:

- values;
- contracts;
- metadata;
- policies;
- abilities;
- equalizer values;
- authority state;
- validation state;
- activation state.

### Situated-depth dimension

The situated-depth dimension establishes where the element exists within meaning, time, authority, causality, composition, dependency, possibility, and runtime use.

It includes:

- recursive composition;
- Kindred position;
- dependency position;
- authority position;
- provenance;
- valid time;
- transaction time;
- causal ancestry;
- causal consequences;
- simulation branches;
- projection ancestry;
- runtime derivation;
- unresolved alternatives;
- potential transformations.

The situated-depth dimension is not merely a visualization or optional graph.

It is a native operational dimension of every Scyon.

## Identity-tier applicability

Scyons are used by all Savant identity tiers except the two atomic tiers.

The atomic exclusions are:

- Iota;
- Mote.

The Scyon-bearing tiers are:

`Trait → Quirk → Prodigal → Exile → Innate → Portal → Obelisk`

Iotas and Motes may be stored, referenced, indexed, composed, validated, and projected through a Scyon belonging to a higher-tier instance.

They do not own independent Scyons.

## Tier scaling

Every Scyon uses the same kernel.

Its legitimate scope and maximum operational capacity are bounded by the identity tier of its owning instance.

A lower-tier Scyon is not a weakened copy or unrelated edition. It is the same organism operating under a narrower profile.

### Trait Scyon

A Trait Scyon governs one stable observable property.

It may manage:

- constituent Motes;
- supporting evidence;
- confidence;
- applicability conditions;
- immediate dependencies;
- local history;
- property validation;
- local projections.

It must not govern broad workflows, jurisdictions, faculties, interaction boundaries, or sovereign systems.

### Quirk Scyon

A Quirk Scyon governs one bounded conditional behavioral pattern.

It adds:

- triggers;
- guards;
- context;
- activation state;
- precedence;
- fallback;
- local side effects;
- behavior replay;
- trigger and non-trigger comparison.

It must remain subordinate to a Prodigal capability.

### Prodigal Scyon

A Prodigal Scyon governs one autonomous reusable capability.

It adds:

- public contracts;
- operational state;
- bounded workflow coordination;
- resources;
- receipts;
- capability extensions;
- local failure containment;
- capability-local simulation.

It must remain subordinate to one primary Exile jurisdiction.

### Exile Scyon

An Exile Scyon governs one enduring operational jurisdiction.

It adds:

- semantic ownership;
- multiple Prodigal coordination;
- domain policy;
- domain dependencies;
- arbitration;
- domain observability;
- domain simulation;
- jurisdictional projections.

The Simulation Exile is expected to use Scyons heavily because its jurisdiction requires branching, causal propagation, metadata interpretation, comparison, recombination, and consequence analysis.

### Innate Scyon

An Innate Scyon governs one constitutional faculty.

It adds:

- multiple Exile coordination;
- faculty guarantees;
- cross-jurisdiction synthesis;
- conflict resolution;
- constitutional constraints;
- fault containment;
- faculty-level projections.

### Portal Scyon

A Portal Scyon governs one living interaction boundary.

It adds:

- ingress;
- egress;
- typed currents;
- protocol mediation;
- user-prompt ingestion;
- access control;
- dynamic projection;
- continuous recomposition;
- external compatibility;
- runtime shard preparation;
- Portal-specific Focal behavior.

A Portal must not use Markdown files as its live database, operational memory, or authoritative state.

Markdown may exist only as an optional human-readable projection or historical artifact.

### Obelisk Scyon

An Obelisk Scyon governs one sovereign foundational system.

It adds:

- multiple Portal coordination;
- constitutional invariants;
- system lifecycle;
- cross-Portal routing;
- system assurance;
- recovery;
- compatibility governance;
- strategic simulation;
- system-level projections.

An Obelisk Scyon must not flatten or duplicate its constituent Portal Scyons.

## Focal law

Every operational Scyon may bind one primary Focal.

The Focal supplies the Scyon’s specialized top layer.

A Focal may define:

- specialized abilities;
- ability presets;
- metadata vocabularies;
- metadata interpretation;
- validation rules;
- policies;
- projections;
- routing behavior;
- automation rules;
- access rules;
- simulation rules;
- equalizer defaults;
- equalizer channel extensions;
- resource profiles;
- event interpretation;
- receipt requirements;
- runtime preparation.

A Focal must not:

- replace the Scyon kernel;
- duplicate kernel substance;
- create independent authority;
- silently alter accepted identity;
- bypass tier limits;
- bypass authority;
- erase history;
- eliminate provenance;
- directly mutate another Scyon;
- absorb constituent Scyons.

Focals are composable specialization layers, not independent database engines.

Scyon abilities are modular and independently registered.

A Scyon may expose dozens or hundreds of abilities, subject to:

- metadata conditions;
- equalizer state;
- available resources;

## Metadata law

Scyons accept arbitrary structured metadata.

Metadata may describe any relevant property, condition, relationship, state, event, assumption, policy, preference, measurement, projection, or runtime concern.

Metadata must support:

- namespace;
- key;
- value;
- value type;
- authority state;
- valid time;
- transaction time;
- provenance;
- lineage where applicable;
- supersession;
- digest;
- applicable scope;
- conditions;
- confidence where applicable.

Metadata may dynamically influence Scyon behavior.

Metadata influence remains constrained by:

- authority;
- tier capacity;
- Focal policy;
- validation;
- equalizer limits;
- security;
- compatibility.

Metadata is not automatically authority.

Open-ended metadata must not become an excuse for storing duplicate canonical substance.

Repeated stable metadata patterns may produce schema proposals.

Schema proposals remain non-authoritative until accepted.

## Equalizer law

Every Scyon may expose a graphic equalizer that fine-tunes the expression of its abilities.

The equalizer does not grant abilities that the owning tier, Focal, authority, dependencies, or resources do not permit.

The effective force of an ability is:

`equalizer value × tier capacity × Focal policy × authority permission × resource availability`

Standard equalizer channels include:

- adaptivity;
- automation;
- authority strictness;
- causal depth;
- composition depth;
- confidence threshold;
- exploration;
- metadata influence;
- projection detail;
- simulation breadth;
- temporal depth;
- validation rigor.

Focals may propose specialized channels.

Specialized channels must:

- declare meaning;
- declare range;
- declare default;
- declare tier applicability;
- declare effects;
- declare conflicts;
- remain inspectable;
- remain testable;
- preserve compatibility.

An equalizer value of `1.0` means the maximum legitimate expression permitted to that Scyon.

It does not remove tier limits.
