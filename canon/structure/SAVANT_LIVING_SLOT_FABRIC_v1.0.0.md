## 1. Purpose

The Living Slot Fabric is Savant's universal attachment mechanism for reusable living substrates.

It does not create a edifice.

It does not create an Exile.

It does not create authority.

It does not duplicate substrate implementations.

It provides typed attachment slots through which any eligible Savant instance may consume one or more instances of the nine canonical living substrates.

The canonical living substrates remain:

1. Scyon
2. Splyce
3. Scrybe
4. Pryme
5. Cypher
6. Thryce
7. Spyral
8. Lythe
9. Dryve

## 2. Governing law

Every stable Savant instance may expose living slots.

A living slot is an attachment point.

A living slot contains a binding reference.

A living slot does not contain copied substrate substance.

Canonical form:

INSTANCE
→ LIVING SLOT
→ BINDING
→ SUBSTRATE INSTANCE
→ SPECIALIZATION
→ CONCRETE CAPABILITY

Bindings may reference:

- Focals;
- overlays;
- masks;
- policies;
- parameters;
- attachments;
- capability contracts;
- adapters;
- compatibility surfaces.

## 3. Nine canonical living slots

The canonical slot taxonomy is:

1. structure
2. interface
3. memory

5. exchange

Canonical substrate mapping:

structure → Scyon

memory → Scrybe

authority → Pryme

exchange → Cypher

derivation → Lythe

The slot names describe capability domains.

They do not transfer operational ownership.

## 4. Jurisdiction law

A living-slot attachment never changes accepted operational jurisdiction.

Examples:

- attaching Dryve does not transfer Niche task authority;
- attaching Dryve does not transfer Opus AI execution authority;
- attaching Thryce does not transfer Notary evidence admission or attestation authority;
- attaching Spyral does not transfer Coda mutation authority;
- attaching Lythe does not transfer Filament projection execution authority;
- attaching Scrybe does not create an independent canonical memory store;
- attaching Pryme does not manufacture authority;
- attaching Splyce does not make presentation authoritative;
- attaching Scyon does not replace the universal Savant instance model.

## 5. Materialization law

Bindings are canonical references or admitted configuration records.

Consumers must not receive copied substrate source trees.

Local directories materialize only when the instance owns local substance that cannot be expressed as:

- a binding;
- an attachment;
- a projection;
- an overlay;
- a Focal;
- a policy;
- a mask;
- a parameter;
- a compatibility adapter.

Unused facilities do not need physical directories.

Existing physical compatibility directories are not destructively removed by adoption of this law.

## 7. Authority

Bindings may be:

- observed;
- proposed;
- provisional;
- accepted;
- superseded;
- rejected.

A binding does not become accepted through repeated use.

Filesystem presence does not establish binding authority.

Confidence does not establish binding authority.

A binding projection does not establish binding authority.

## 8. Composition

An owner may consume multiple living slots.

A slot may support multiple compatible substrate instances when their identities and roles do not conflict.

A binding may depend on other bindings.

Dependency cycles are invalid unless a specific accepted contract explicitly permits recursion.

Default dependency topology is acyclic.

## 9. Inheritance

Living-slot bindings may be inherited only through explicit composition or an accepted inheritance relation.

Filesystem ancestry is insufficient.

Inherited bindings remain references to the original binding.

Consumers may add specialization overlays without copying the inherited substrate.

## 10. Extra slots

The nine living slots are the canonical reusable substrate slots.

Instances retain their existing extension and future-extension capacity.

Additional domain-specific slots may be created where separately justified.

The nine living slots do not exhaust the universal attachment model.

## 11. Cardinality

The nine-slot taxonomy exists because it maps directly to nine independently defined living substrate domains.

No element must populate all nine.

No collection is padded merely to satisfy cardinality.

An instance may use:

- zero slots;
- one slot;
- several slots;
- all nine slots;

according to actual capability requirements.

## 12. Projection

Living-slot views are deterministic projections.

- dependency graphs;
- capability views;
- health views;
- compatibility views;
- UI views;
- integration views.

Projection does not create authority.

## 16. Dependency policy

The baseline implementation must function with the Python standard library.

Existing Savant dependencies may accelerate validation when available:

- jsonschema for Draft 2020-12 contract validation;
- networkx for graph validation and topological projection.

They are accelerators.

They are not authority.

Failure to import an optional accelerator must not make canonical bindings unreadable.

## 17. Migration

No physical migration is authorized by this contract.

Adoption sequence:

1. create the shared registry;
2. create binding manifests;
3. validate bindings;
4. project consumers;
5. bind existing capabilities through compatibility surfaces;
6. stop creating unnecessary duplicated substrate structures;
7. prove consumers;
8. retire duplication only through normal migration authority.

## 18. Structural consequence

The Living Slot Fabric becomes the canonical connective mechanism between universal instances and living substrates.

It strengthens:

- modularity;
- substrate reuse;
- attachment semantics;
- graph transparency;
- compatibility;
- extension;
- observability;
- deterministic composition.

It does not replace:

- Rubrics;
- Cabals;
- Kindred;
- Segues;
- Moods;
- ordinary Slots;
- Attachments;
- operational Exile ownership.

Those mechanisms remain independently meaningful and may participate in living-slot specialization.
