# NICHE EXILE CANON

Version: 1.0.0
Status: PROPOSED CANON
Date: 2026-08-07
Identity: exile:niche

---

## 1. IDENTITY

Niche is Savant's Task Exile.

Niche is implemented as:

Exile-tier Scyon
+ Niche Focal
+ Niche composition
+ Niche authority
+ Niche relationships
= Niche

Niche must not duplicate the Exile-grade Scyon baseline.

---

## 2. PURPOSE

Niche transforms goals into finite, dependency-closed, priority-governed, capability-addressable, evidence-completable work graphs.

Niche is the supervisor of work.

It determines:

- what work exists;
- what work is required;
- what work is important;
- what work is optional;
- how work decomposes;
- what depends on what;
- what is blocked;
- what can execute now;
- what can execute in parallel;
- what must happen first;
- what evidence proves completion;
- when the requested work is finished.

---

## 3. PRIORITY MODES

Niche has three canonical priority modes.

### Mode 1 — Mandatory

Includes only the minimum dependency-closed work required to achieve the requested outcome.

### Mode 2 — Salient

Includes Mandatory plus materially important work whose omission would significantly weaken the result.

### Mode 3 — Arbitrary

Includes Mandatory, Salient, and the entire legitimate optional work universe.

This may include:

- enhancements;
- optimizations;
- alternatives;
- contingencies;
- research;
- polish;
- future extensions;
- optional validation;
- optional observability;
- other admissible work.

Arbitrary does not mean random.

---

## 4. CANONICAL MODE INTERPRETATION

Mode 1 = minimum complete.

Mode 2 = strategically complete.

Mode 3 = exhaustively complete.

Mode 1 is the default mechanism for preventing runaway implementation when only required work was requested.

---

## 5. NINE-PART PRIORITY RECORD

Every Niche priority classification may expose:

1. intrinsic_priority
2. effective_priority
3. priority_context
4. priority_scope
5. promotion_chain
6. demotion_constraints
7. authority_source
8. classification_rationale
9. confidence

---

## 6. INTRINSIC AND EFFECTIVE PRIORITY

Intrinsic priority describes the task independent of temporary dependency pressure.

Effective priority describes the priority required by the present execution context.

They must remain distinct.

A task's intrinsic classification is not rewritten merely because another task temporarily requires it.

---

## 7. PRIORITY CLOSURE

Priority Closure is a core Niche capability and a reusable shared Scyon ability.

Example:

Task A:
mandatory

Task B:
salient

A depends on B.

Then:

B.intrinsic_priority = salient

B.effective_priority = mandatory

B.promotion_chain = prerequisite_of:A

The promotion must preserve its reason and provenance.

---

## 8. ROADMAP PRIORITY BANDS

Existing roadmap bands remain orthogonal to the three priority classes.

Mandatory/Salient/Arbitrary determine inclusion.

Roadmap bands determine ordering among admitted work.

Neither replaces the other.

---

## 9. PRIORITY CONTEXT

Priority is contextual.

A capability may be arbitrary for one task and mandatory for another.

Classification may consider:

- governing goal;
- dependencies;
- authority;
- risk;
- deadline;
- reversibility;
- blast radius;
- compatibility;
- completion requirements;
- execution environment.

---

## 10. PRIORITY SCOPE

Priority scope identifies the frame in which a classification applies.

It works with Horizon but is not identical to Horizon.

Potential scope includes:

- immediate operation;
- current task;
- governing goal;
- project;
- system;
- recursive dependency context.

---

## 11. CONFIDENCE

Priority classification carries confidence.

Confidence must expose enough basis to distinguish:

- authoritative classification;
- deterministic derivation;
- evidence-backed classification;
- inference;
- uncertainty.

Low-confidence priority must not silently masquerade as authority.

---

## 12. HORIZON

Niche supports:

- immediate;
- bounded;
- project;
- system;
- recursive.

Mode and Horizon are independent.

Examples:

mandatory + immediate:
only what must happen next.

mandatory + system:
all mandatory work required for system completion.

arbitrary + recursive:
the complete recursively reachable legitimate work universe.

---

## 13. WORK UNIVERSE

Niche distinguishes:

Work Universe:
all discovered admissible work.

Mode Projection:
work admitted by selected priority mode.

Dependency Closure:
all prerequisites required by admitted work.

Execution Frontier:
work executable now.

Dispatch Set:
work selected to execute now.

These concepts must not be conflated.

---

## 14. GOAL CLOSURE

Niche must determine the minimum complete work topology required to satisfy a goal.

Goal Closure prevents endless adjacent work from being mistaken for completion requirements.

---

## 15. DEPENDENCY CLOSURE

A selected task set is not executable until its required dependency closure is known.

Dependency Closure may recursively promote otherwise lower-priority work.

---

## 16. EXECUTION FRONTIER

Niche must expose the subset of admitted work executable now.

Executors should not need the entire future work graph merely to perform the current operation.

---

## 17. SCOPE GRAVITY

Every task must have a traceable contribution path to its governing goal.

Niche may expose:

- goal distance;
- dependency distance;
- authority distance;
- completion contribution;
- scope gravity.

Tasks without a legitimate contribution path are orphaned, unrelated, or scope-creep candidates.

---

## 18. FINITE COMPLETION

Every Niche planning request must have an explicit stopping condition.

Niche must resolve:

- exact outcome;
- governing goal;
- scope;
- priority mode;
- horizon;
- dependency closure;
- completion predicates;
- evidence requirements;
- blockers;
- execution frontier;
- stopping condition.

Once these are satisfied, the task is complete.

Niche must stop.

---

## 19. TASK IDENTITY

Tasks require stable identity.

Equivalent task substance should not proliferate merely because wording changes.

Task identity should support deterministic fingerprints where appropriate.

Semantic similarity alone must not silently merge authoritative task identities.

---

## 20. TASK LINEAGE

Niche must preserve:

- decomposition parentage;
- splits;
- merges;
- derivations;
- supersessions;
- reopenings;
- reclassifications;
- previous states.

History must not be destroyed merely because the current projection changes.

---

## 21. TASK PROVENANCE

Niche must preserve why a task exists.

Potential provenance includes:

- user directive;
- accepted decision;
- authority requirement;
- dependency derivation;
- evidence;
- implementation defect;
- migration requirement;
- validation failure;
- planning derivation.

---

## 22. COMPLETION

Completion is evidence-backed.

A task is not complete merely because a boolean field was changed.

Completion may require:

- predicates;
- artifacts;
- validation;
- receipts;
- evidence;
- integration checks;
- authority confirmation.

Requirements depend on task type and risk.

---

## 23. TASK GRAPH

Niche task topology should support, where useful:

- ancestors;
- descendants;
- dependencies;
- dependents;
- topological ordering;
- cycle detection;
- transitive closure;
- transitive reduction;
- critical path;
- parallel generations;
- dominators;
- blocker propagation;
- impact propagation.

External graph libraries may assist implementation but never become authority.

---

## 24. TASK SHATTERING

Oversized work may be recursively decomposed until executable.

Decomposition must preserve:

- parent goal;
- lineage;
- dependencies;
- authority;
- completion contribution.

Decomposition must not create meaningless microtasks merely to increase granularity.

---

## 25. TASK FUSION

Equivalent or compatible work may be represented once with multiple dependents where authority and semantics permit.

Fusion must not erase distinct authoritative identities.

---

## 26. PARALLELISM

Niche should identify independent work that can execute concurrently.

Parallelism must respect:

- dependencies;
- resources;
- locks;
- authority;
- side effects;
- work-in-progress limits.

---

## 27. CRITICAL PATH

Niche should identify work controlling earliest possible goal completion when duration information is sufficient.

Critical-path analysis is a planning projection, not authority.

---

## 28. BLOCKERS

Blockers propagate through dependents.

Niche must distinguish:

- blocked;
- waiting;
- not ready;
- unauthorized;
- missing dependency;
- failed prerequisite;
- unavailable capability.

---

## 29. RISK

Task risk may include:

- impact;
- likelihood;
- reversibility;
- blast radius;
- failure modes;
- mitigations.

Risk may influence effective priority.

Risk does not independently rewrite authority.

---

## 30. DEADLINES

Where deadlines exist, Niche may calculate:

- prerequisite deadlines;
- latest safe start;
- slack;
- critical timing;
- deadline risk.

Deadline calculations remain projections over authoritative dates and task topology.

---

## 31. RESOURCES

Niche may plan around:

- time;
- compute;
- tokens;
- money;
- API capacity;
- memory;
- concurrency;
- human attention;
- locks;
- provider availability.

---

## 32. CAPABILITY MATCHING

Niche schedules capabilities rather than hardcoding implementation details where possible.

It may match work to:

- Exiles;
- Prodigals;
- programs;
- tools;
- providers;
- humans;
- external executors.

Capability matching does not transfer semantic ownership.

---

## 33. AUTHORITY-AWARE PLANNING

Niche may discover work without being authorized to execute it.

Discovery is not authority.

Planning is not authority.

Projection is not authority.

Niche must preserve the distinction between:

- proposed;
- admitted;
- authorized;
- executable;
- completed.

---

## 34. REPLANNING

When authoritative reality changes, Niche should replan only the affected graph region when possible.

Replanning may be triggered by:

- dependency changes;
- authority changes;
- execution results;
- deadlines;
- risk;
- evidence;
- resource availability;
- failure;
- supersession.

---

## 35. PLAN DIFFING

Niche should explain changes between plan versions.

A plan diff may expose:

- tasks added;
- tasks removed;
- priority changes;
- promotions;
- demotions;
- new blockers;
- resolved blockers;
- changed dependencies;
- changed frontier;
- changed completion conditions.

---

## 36. PLAN REPLAY

Given authoritative inputs and immutable task history, Niche should be able to reconstruct its current plan state deterministically where feasible.

Replay is a core enterprise-grade property.

---

## 37. ALTERNATIVE PATHS

Niche may represent multiple legal routes to a goal.

It must not prematurely collapse alternatives into one path when authority or evidence does not justify doing so.

---

## 38. CONDITIONAL TASKS

Tasks may activate only when explicit predicates become true.

Conditional work should not pollute the active execution frontier before its condition is satisfied.

---

## 39. CONTINGENCIES

Failure branches may be planned in advance.

Contingency existence does not make contingency execution mandatory unless its trigger occurs.

---

## 40. ATTENTION GOVERNOR

Mode 3 may expose an enormous work universe.

Niche must prevent optional discovery from contaminating mandatory execution.

The Attention Governor limits what is surfaced to executors according to:

- mode;
- horizon;
- frontier;
- context;
- budget;
- relevance.

---

## 41. WORK-IN-PROGRESS LIMITS

Niche may restrict simultaneous active work to prevent execution fragmentation.

WIP limits are resource/execution controls, not semantic priority.

---

## 42. SCOPE-CREEP DETECTION

Niche should detect work entering a plan without a valid contribution path to the governing goal.

Mode 1 applies the strongest rejection.

Mode 3 may expose weakly related legitimate work but must label it honestly.

---

## 43. STALENESS

Tasks derived from superseded or changed evidence may become stale.

Staleness should propagate to dependent projections where appropriate.

---

## 44. ORPHAN DETECTION

Tasks that no longer contribute to an accepted goal should be detectable.

Orphaned work must not silently remain mandatory.

---

## 45. WHAT-IF SIMULATION

Niche may support non-mutating simulations such as:

- remove task;
- delay task;
- fail task;
- change resource;
- change priority;
- change deadline;
- choose alternate path.

Simulation does not mutate live authority or task state.

---

## 46. VALUE/COST PROJECTION

Where evidence permits, Niche may compare material value against cost.

This is especially useful for Salient and Arbitrary work.

Value/cost estimates must remain distinguishable from authoritative facts.

---

## 47. MASTERPLAN

Masterplan is a Niche specialization.

Masterplan governs Savant-wide roadmap/task planning.

Niche is broader than Masterplan.

Other task systems may use Niche without becoming Masterplan.

---

## 48. NICHE BOUNDARIES

Niche owns:

- task discovery;
- task decomposition;

- task queues;
- task leases;

Niche retains semantic authority over task priority.

## 51. UNIVERSAL VS NICHE-SPECIFIC CLASSIFICATION

Before implementing any Niche feature, classify it.

implement once as shared Scyon capability and instance it.

implement under Niche specialization.

This classification happens before code is written.

## 55. IMPLEMENTATION SEQUENCE

Niche is the next major Exile implementation after the current Scyon/Living Structure task is complete.

The sequence is:

1. finish Scyon/Living Structure;
2. inspect current Niche and Masterplan implementation;
3. preserve verified behavior;
4. identify universal vs Niche-specific features;
5. implement missing shared Scyon abilities first;
6. instantiate Exile-tier Scyon for Niche;
7. create/apply Niche Focal;
8. preserve and integrate Masterplan;
9. implement required Niche-specific enhancements;
10. perform minimum sufficient validation;
11. stop when Niche meets its completion conditions.

## 57. CANONICAL NICHE STATEMENT

Niche is Savant's Exile-tier Scyon specialization for the discovery, decomposition, prioritization, topology, scheduling, coordination, and evidence-backed completion of work.

Niche transforms goals into finite executable work graphs.

Its three priority modes are Mandatory, Salient, and Arbitrary.

Its priority system preserves intrinsic priority separately from effective contextual priority.

Its defining advanced mechanism is Priority Closure.

Niche uses the universal Exile-grade Scyon baseline rather than duplicating common Exile behavior.

Niche owns task semantics.

Shared Scyon abilities remain shared.

Masterplan is a Niche specialization.

Niche stops when the requested work is demonstrably complete.
