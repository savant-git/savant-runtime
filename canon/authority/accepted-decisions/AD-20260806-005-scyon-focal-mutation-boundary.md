# AD-20260806-005: Scyon and Focal Mutation Boundary

## Status

Accepted

## Date

2026-08-06

## Authority

Current user directive and accepted Scyon/Focal architecture.

## Supersedes

This decision supplements and supersedes AD-20260806-004 only where AD-004 is incomplete concerning mutation, migration, destructive replacement, and implementation-transition authority.

All compatible Scyon/Focal architecture established by AD-20260806-004 remains accepted.

AD-20260806-004 remains immutable historical authority and must not be edited merely to add this missing boundary.

## Preserved Scyon/Focal architecture

The following established architecture remains authoritative:

- Scyon is the canonical term for the modular three-dimensional Savant database organism.
- Focal is the canonical term for the specialized top layer applied to a Scyon.
- Every Scyon derives from one shared modular Scyon kernel.
- Scyons are used from Trait through Obelisk.
- Iota and Mote are atomic exclusions and do not independently own Scyons.
- Higher-tier Scyons increase operational scope without duplicating lower-tier canonical substance.
- Focals specialize Scyons without replacing or independently reimplementing the shared kernel.
- Scyons support arbitrary structured metadata.
- Metadata may dynamically influence behavior but is not automatically authority.
- Scyons may expose modular abilities and graphic-equalizer controls.
- Tier capacity bounds legitimate Scyon behavior.
- Portal Scyons are living, dynamic, continuously recomputed interaction boundaries.
- Portal-specific behavior is supplied through Focals.
- Portal operation must not depend upon Markdown as its live database or operational state.
- Simulation uses Scyons heavily for branch, causal, assumption, consequence, and counterfactual state.
- Simulation branches are non-authoritative by default.
- Projections are derived and must not become duplicate authority.
- Technology choice does not itself establish authority.

## Extension-before-replacement law

Scyon/Focal implementation must proceed through extension and compatibility before replacement.

The preferred progression is:

`existing implementation → compatibility mapping → Scyon/Focal successor → parallel validation → explicit migration → compatibility retirement`

Replacement is not the first implementation step.

## Identity preservation law

Migration must not change identity merely because paths, class names, database names, tables, fields, APIs, or terminology change.

Every migrated identity must preserve or explicitly supersede:

- stable identity;
- archetype;
- tier;
- lineage;
- provenance;
- constituents;
- dependencies;
- dependents;
- authority;
- compatibility;
- succession;
- extension points.

Where exact preservation is impossible, migration must stop unless accepted authority explicitly resolves the incompatibility.

## Substance preservation law

Canonical substance must not be copied into new Scyon structures merely to make migration easier.

Scyon migration must prefer:

- references;
- adapters;
- deterministic projections;
- compatibility mappings;
- typed transformations.

Duplicate authoritative stores are prohibited unless separately authorized for a bounded transition with an explicit reconciliation mechanism.

## Database migration law

A database-engine transition is not implied by Scyon adoption.

Scyon is an architectural and semantic identity, not a mandate for a specific database product.

Existing storage may remain in place when compatible.

Where successor storage is required, migration must preserve:

- authoritative primitives;
- event history;
- temporal semantics;
- metadata;
- relations;
- lineage;
- provenance;
- compatibility;
- receipts;
- replay;
- recovery.

## Focal migration law

Existing behavior equivalent to future Focal behavior must first be discovered and mapped.

A Focal must not be introduced by duplicating behavior already owned elsewhere.

Existing:

- policies;
- validators;
- adapters;
- providers;
- projections;
- capability modules;
- routing;
- runtime configuration;
- specialization logic;

must be inventoried before equivalent Focal functionality is created.

Where existing functionality is authoritative and compatible, the Focal should compose or reference it.

## Validation law

No migration stage may claim success from syntax validity alone.

Minimum validation for a Scyon/Focal migration stage is:

1. syntax or compilation;
2. one focused functional verification;
3. one relevant startup, compatibility, or integration verification.

Additional validation is required when persistent data, shared interfaces, authority, destructive mutation, or many dependents are affected.

## Rollback law

Any authorized destructive migration must have a deterministic rollback path before execution unless rollback is provably unnecessary and accepted authority explicitly permits omission.

Rollback must preserve the pre-migration authoritative state.

## Receipt law

Every authorized migration operation must emit sufficient evidence to establish:

- source identity;
- source digest;
- destination identity;
- destination digest;
- transformation;
- authority;
- dependencies;
- compatibility result;
- validation result;
- timestamp;
- rollback reference.

## Completion condition

Scyon/Focal physical migration remains incomplete until:

- migration authority exists;
- all required prerequisites are satisfied;
- transformation passes validation;
- required compatibility remains functional;
- persistent data is preserved;
- rollback exists where required;
- receipts exist;
- no known blocker prevents use.
